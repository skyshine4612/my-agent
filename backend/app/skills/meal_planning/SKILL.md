# 饮食规划

规划饮食/食谱时，遵循以下规则：

- 菜谱用 `recipe_search` 搜索（按菜名或食材关键词），拿到 id 后用 `recipe_detail` 查做法和食材用量。
- 减脂、增肌、控糖等需要算热量的场景，用 `ingredient_nutrition` 查食材营养成分（热量/蛋白质/脂肪/碳水/膳食纤维）。
- 时令食材结合 `holiday_calendar`（节气）判断；通用饮食知识用 `tavily_search` 补充，但具体菜谱做法以 `recipe_detail`
  为准，不要用搜索编造步骤。
- **同一套方案内部**的多个独立查询（多个菜谱、多种食材）应在同一轮并行调用，不要逐个串行等待，也不要为此委派子任务。
- 天数按用户要求（未指定默认一周），输出：食谱表（早/中/晚）+ 采购清单（按菜谱食材汇总）+ 热量/营养标注（减脂场景）。
- 每天的菜不要重复：荤菜、素菜尽量**在同一套方案内**全程不重样，避免同一道菜反复出现。
- 默认给 1 套方案即可；只有用户明确要求（如「给几个方案」「多套方案」）时才给 2-3
  套不同侧重点的方案（如「高蛋白低脂」「快手省时」「食材易买」），每套的食谱表、采购清单、营养标注都完整写出。
- **多套方案时按套委派 `call_sub_agent`**：直接按套数委派 2-3 个子任务，每个负责一套方案。
  **委派前不需要先自己查任何数据**——本业务的输出模板（食谱表 / 采购清单 / 营养标注）不含需要你预先取回的共享字段，
  子任务各自查自己那套要用的菜谱即可。（`holiday_calendar` 是可选的时令参考，不是前置步骤，更不要反复查。）
  - 每次委派都要给 `title`（8 字以内的短标题，如「高蛋白低脂」）。并行的几个子任务标题必须互不相同，
    用户在界面上就是靠它区分哪个是哪个。
  - task 里必须写清用户的天数、口味偏好、忌口与热量目标，并要求子助手**按输出模板的字段返回片段**
    （如「返回食谱表（第1天~第N天 × 早/中/晚）+ 采购清单 + 营养标注三段」），不要让它写散文——模板要用原始字段填。
  - **不要按天扇出**：「不重样」是跨天的全局约束，按天拆开的话各个子任务互相看不见对方选了什么，必然重样。
    扇出的粒度只有「套」，一套方案必须由一个子任务从第一天排到最后一天。
- 信息不足时先基于合理假设推断并明确提示用户，不要反复追问。

## 输出格式

严格按下面这个模板输出（标题、顺序、层级一字不改，不要每次换排版）。
模板里的 `{…}` 是占位符，输出时替换成真实内容，**不要把花括号本身、也不要把下面这些说明文字抄进答案**：

```markdown
### {目标} 饮食规划

**食谱表**

| 日期 | 早餐 | 午餐 | 晚餐 |
| --- | --- | --- | --- |
| 第1天 | {…} | {…} | {…} |
| 第2天 | {…} | {…} | {…} |

**采购清单**
- 肉类：{…}
- 蔬菜：{…}
- 主食：{…}
- 其他：{…}

**营养标注**

| 食材 | 热量 | 蛋白质 |
| --- | --- | --- |
| {…} | {…} | {…} |
```

模板各节的内容约定：

- `**食谱表**`：行数 = 用户要求的天数（未指定按一周），第 N 行的行首是「第N天」；单元格写菜名，多个用「、」分隔。
- `**采购清单**`：按类别分组，每项写「食材 + 大致用量」（如「猪瘦肉 300g」）；类别按本方案实际用到的食材增减。
- `**营养标注**`：减脂 / 增肌 / 控糖场景用上面的表格，热量与蛋白质来自 `ingredient_nutrition`；
  家常场景**不用表格**，改写成一句话概括搭配原则（如「荤素搭配，蛋白质与膳食纤维充足」）。

**多套方案时**：上面这一整块（标题 + 三节）**每套各写一遍**，标题带侧重点后缀区分，
如 `### 一周减脂饮食规划 · 高蛋白低脂`、`### 一周减脂饮食规划 · 快手省时`；不要把多套揉进同一张表。
单套方案时标题不加后缀。
